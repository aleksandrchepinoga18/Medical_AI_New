## Сверка плана с ТЗ и архитектурой

Прямых архитектурных противоречий в заданиях этапов 2–10 не обнаружено:
сохраняются модульный монолит, существующие хранилища и Celery, локальная LLM
до подключения внешних адаптеров, согласия и запрет скрытого fallback.
Требования ТЗ действуют полностью, даже если краткое задание их не повторяет:
безопасные cookie-сессии (§8), проверка файлов и лимиты (§5.1), обработка всего
релевантного текста при извлечении показателей, а не только top-k (§5.3),
защита от prompt injection и отсутствие чувствительных данных в логах (§8).

Пробелы и вопросы, требующие согласования без самостоятельного изменения архитектуры:

- MLflow SDK, эксперименты и Registry lifecycle есть в общем обзоре и архитектуре,
  но не назначены конкретному этапу 2–10. Autologging/tracing не включать автоматически;
  до логирования нужны redaction, согласия, ACL, retention и удаление (§9.5).
- Расширение CI отнесено к этапу 9; проверки миграций и интеграционные тесты нужны
  уже с появлением соответствующих функций (§9.2–9.3). Задание этапа 2 требует тесты,
  но срок их включения в CI явно не определён.
  По поручению на этап 2 добавлен отдельный CI job с PostgreSQL для миграций
  и auth integration tests; расширенный CI/CD остаётся задачей этапа 9.
- LangGraph/Airflow рассматриваются на этапе 10, но независимые интерфейсы,
  идемпотентность и версии необходимо учитывать при разработке предыдущих этапов (§10).

Основа этапа 2 по исходникам: FastAPI liveness, Settings и Celery без бизнес-задач;
Next.js App Router с начальной страницей и health endpoint. SQLAlchemy, драйвер
PostgreSQL и Alembic в backend пока отсутствуют; настроек подключения приложения
к PostgreSQL нет. Это работа этапа 2, а не ошибка работающей инфраструктуры этапа 1.
Compose содержит отдельные PostgreSQL 17.6 для приложения и MLflow, internal-сети
и постоянные тома; порты БД на хост не опубликованы. Миграции приложения не должны
затрагивать `mlflow-db`, существующие данные, имена томов и `COMPOSE_PROJECT_NAME`.

## Реализуй этап 4 Medical AI — персональный RAG:

Работай в существующем проекте Medical AI. Сначала изучи текущую архитектуру, модели PostgreSQL, обработку документов, Celery, Redis, Qdrant, конфигурацию Docker Compose и существующие тесты. Не дублируй уже реализованные компоненты.

### 1. Chunking и подготовка данных

- Разбивай извлечённый текст PDF/DOCX на чанки с настраиваемыми размером и перекрытием.
- Сохраняй `user_id`, `document_id`, `text_version_id`, `chunk_id`, порядковый номер и доступную информацию об источнике (страница, блок).
- Не смешивай данные разных пользователей.
- Обеспечь детерминированные идентификаторы чанков и идемпотентность обработки.

### 2. Embeddings и Qdrant

- Реализуй адаптер для локальной модели embeddings через Ollama.
- Предусмотри конфигурацию модели, размерности векторов, таймаутов и batch size.
- Проверяй совместимость размерности модели с коллекцией Qdrant.
- Реализуй создание коллекции, payload indexes, загрузку и удаление векторов.
- Не удаляй существующие коллекции и данные при инициализации.

### 3. Фоновая индексация

- Используй существующие Celery и Redis.
- Индексируй документы после успешного извлечения текста.
- Предусмотри повторные попытки, восстановление после сбоев и защиту от параллельной индексации одной версии.
- Повторная индексация должна исключать дубликаты и не оставлять устаревшие версии доступными для поиска.
- Сбой Ollama или Qdrant не должен менять статус успешно обработанного исходного документа на `failed`.
- Предусмотри отдельные статусы индексации.

### 4. Семантический retriever

- Реализуй поиск по Qdrant с обязательной серверной фильтрацией по `user_id`.
- Учитывай актуальную версию текста и статус документа.
- Возвращай найденные фрагменты, score, идентификаторы документов и ссылки на страницы/блоки.
- Не доверяй `user_id`, переданному клиентом: определяй владельца из авторизованной сессии.
- Защити систему от утечки данных между пользователями.

### 5. API и интерфейс

- Добавь защищённый FastAPI endpoint для семантического поиска.
- Добавь API для просмотра статуса индексации и повторной индексации.
- Интегрируй поиск в существующий Next.js frontend без нарушения авторизации и CSRF-защиты.
- Показывай пользователю найденные фрагменты и их источники.

### 6. Evaluation и тесты

- Добавь небольшой воспроизводимый evaluation-набор на синтетических документах.
- Рассчитывай Recall@K, MRR@K и nDCG@K.
- Проверь идемпотентность, повторную индексацию, удаление, восстановление после ошибок и изоляцию пользователей.
- Используй отдельное тестовое окружение, не затрагивающее рабочие данные.
- Подготовь инструкции для ручного запуска тестов и проверки результатов.

### 7. Ограничения

- Не подключай пока медицинский веб-поиск, LLM-чат, LangGraph и сложного агента.
- Не реализуй BM25 и reranker на этом этапе — оставь архитектуру расширяемой для их подключения.
- Не удаляй существующие Docker volumes, базы данных, коллекции Qdrant и документы.

- Не изменяй существующие секреты и не выводи содержимое `.env`.
- Не запускай Docker, миграции, тесты, npm-команды и Git-команды. Все команды выполню самостоятельно.

Создай полноценный чат в Next.js, хранение диалогов в PostgreSQL, ответы с контекстом персонального RAG и проверяемыми ссылками на документы. Архитектура Gateway должна поддерживать будущие OpenAI, DeepSeek, YandexGPT и GigaChat. Не передавай данные внешним провайдерам. Добавь тесты и команды ручной проверки.

## Реализуй этап 6 Medical AI: 
независимый медицинский RAG с управляемым корпусом источников, метаданными публикаций, версиями, статусами проверки и разграничением персональных данных. Добавь контролируемый инструмент веб-поиска по разрешённым медицинским источникам, с проверкой ссылок и происхождения информации. Чат должен различать личные результаты, общие медицинские сведения и найденные внешние рекомендации. Добавь тесты и ограничения безопасности. Не запускай команды.

## Реализуй этап 7 Medical AI: 
подключаемые адаптеры OpenAI, DeepSeek, YandexGPT и GigaChat через существующий LLM Gateway. Учитывай различия авторизации, streaming, структурированного вывода и лимитов API. Добавь управление провайдерами, учёт токенов и стоимости, защищённое хранение ключей, явное согласие пользователя на передачу медицинских данных и запрет несанкционированного fallback. Добавь тесты с mock API без реальных платных вызовов. Не запускай команды.

## Реализуй этап 8 Medical AI: 
извлечение всех лабораторных показателей из документов с помощью LLM и структурированного JSON. Добавь Pydantic-валидацию, проверку чисел по исходному тексту, ручное подтверждение, сохранение показателей в PostgreSQL, сравнение по датам, графики и отчёты. Точные расчёты выполняй через SQL/Python. Не разрабатывай универсальный rule-based медицинский парсер. Добавь размеченные тестовые данные и оценку качества извлечения. Не запускай команды.

## Реализуй этап 9 Medical AI: 
production-конфигурации, расширенный GitHub Actions CI/CD, сборку и публикацию Docker-образов в GHCR, staging/production workflow, контролируемые миграции, smoke tests, rollback приложения, мониторинг Prometheus/Grafana/OpenTelemetry, резервное копирование и инструкции восстановления. Добавь security и performance checks, эксплуатационную документацию. Не выполняй деплой, Docker-команды, тесты и миграции самостоятельно.

## Реализуй этап 10 Medical AI: 
проверь готовность существующей архитектуры к интеграции LangGraph для AI-workflows и Apache Airflow для периодических data pipelines. Выдели стабильные интерфейсы инструментов retrieval, SQL/Python, LLM Gateway и поиска. Подготовь архитектурную документацию, контракты, тесты совместимости и план интеграции. Не устанавливай LangGraph и Airflow без отдельного согласования. Не запускай команды самостоятельно.
