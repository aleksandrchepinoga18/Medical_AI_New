# Изолированный benchmark извлечения документов

Скрипт из каталога `backend` генерирует восемь PDF из фиксированного синтетического
эталона. Он принимает только ID из эталона. Каждый запуск сохраняет PDF и
`report.json` в новом локальном каталоге. Отчёт содержит SHA-256 эталона и
PDF, версии корпуса, отчёта и PyMuPDF, ожидаемые записи, результаты и источники
по каждому файлу. Эталон задаёт 23 измерения. Один PDF содержит только реквизиты.

В корпусе v2 ячейка µg/L в 02-borderless печатается встроенной Helvetica
с латинской кодировкой. У прежнего шрифта Droid Sans Fallback в PyMuPDF 1.26.6
нет глифа U+00B5. Эталонные значения и позиции строк сохранены. Новый запуск
записывает SHA-256 манифеста v2 и сгенерированных PDF. Сверяйте версию и хеши
при сравнении запусков.

| ID | Особенность |
| --- | --- |
| `01-grid` | Русская таблица с границами |
| `02-borderless` | Английская таблица без линий |
| `03-wrapped` | Переносы внутри ячеек, даты в отдельной колонке |
| `04-multipage` | Две страницы, одинаковые названия и повторяющееся значение с разными датами |
| `05-long-header` | Длинная шапка с реквизитами, значения и референсы со знаками |
| `06-scan` | PDF из растровой страницы |
| `07-mixed` | Векторная таблица и страница с текстовой шапкой и растровой таблицей |
| `08-no-measurements` | Реквизиты и числа без измерений |

## Итоги корпуса v2

Backend использует тот же HTTP-адаптер. Настройки, API и ручные проверки
описаны в [документации извлечения](DOCUMENT_EXTRACTION.md).

В пяти сохранённых отчётах совпадают эталон, порядок восьми PDF, их SHA-256,
версия схемы отчёта и PyMuPDF 1.26.6. Хеши сверены с 40 сохранёнными PDF,
хеш манифеста совпадает с файлом в репозитории. Локальные предсказания
одинаковы во всех пяти отчётах. Источники — `report.json` в каталогах
`local-v2`, `ultra-v2`, `max-v2`, `pro-v2` и `lite-v2`.

В каждом прогоне 23 эталонные записи. Совпадения считаются по пяти полям записи.
Для Ultra и Max все 23 страницы, указанные для сопоставленных по названию
записей, верны. PyMuPDF Tables пропустил четыре измерения на растровых
страницах `06-scan` и `07-mixed`. Медиана включает все восемь попыток, в том
числе ошибки. Токены — сумма API `usage.total_tokens`. Доля кэшированного входа
различалась между моделями, поэтому значения описывают эти прогоны.
[Подсчёт токенов GigaChat](https://developers.sber.ru/docs/ru/gigachat/guides/counting-tokens)

Все четыре удалённых прогона записали `schema` и фактические версии моделей.
У Ultra это `32.9.16.9`, у остальных — `2.0.30.01`. Единый адаптер задаёт
`max_tokens=2500`, `temperature=0.1`, `stream=false`, `function_call="auto"` и
строгую JSON-схему для одного PDF на запрос. В сохранённых отчётах есть режим,
версия модели и расход токенов. Прочие параметры сверены по коду, поскольку
снимок запроса в отчёты не записывался.
[Общий HTTP-адаптер](../backend/app/documents/gigachat.py)

### Причины расхождений

- У **Max** три несовпадения в `05-long-header` на странице 1. Для С-реактивного
  белка, триглицеридов и тромбоцитов модель перенесла `2026-10-01` из надписи
  «Бланк № 4202 от 2026-10-01» в поле `date`. В эталоне дата измерения для всех
  трёх строк отсутствует. Значения, единицы, референсы, названия и страница
  совпали. Lite выполнил тот же перенос для этих трёх строк.
- У **Pro** нулевой F1 объясняется двумя проблемами. В пяти усечённых ответах
  адаптер отбросил весь результат. В двух завершённых ответах по `01-grid`
  и `02-borderless` у всех семи записей поле `date` содержит строку
  `"null"` вместо JSON `null`. Текущая схема `str | None` допускает
  такую строку. Поле даты исключает все семь записей из полных совпадений.

### Завершение по длине

| Модель | Документ и `completion_tokens` при `length` |
| --- | --- |
| Pro | `03-wrapped` 140, `04-multipage` 112, `05-long-header` 94, `06-scan` 127, `07-mixed` 95 |
| Lite | `01-grid` 80, `06-scan` 78 |

API вернул `finish_reason="length"`. Адаптер сначала сохраняет `usage` и
версию модели, затем допускает Pydantic-валидацию только при `stop`.
Поэтому усечённые ответы дают `completion_unfinished_length` и не публикуют
измерения. Официальный SDK Structured Output тоже считает `length` усечением.
Документированное окно Lite и Pro составляет 128 000 токенов. Это размер
контекста. Отдельный эффективный предел вывода при сочетании PDF и строгой
схемы в документации не указан.
[Справка GigaChat](https://developers.sber.ru/docs/ru/gigachat/api/grpc/grpc-methods) ·
[Lite](https://developers.sber.ru/docs/ru/gigachat/models/gigachat-2-lite) ·
[Pro](https://developers.sber.ru/docs/ru/gigachat/models/gigachat-2-pro) ·
[SDK GigaChat](https://github.com/ai-forever/gigachat#structured-output-json-schema--beta)

Значения 78–140 существенно ниже заданных 2500. Те же версии Pro и Lite
успешно завершили ответы с 371 и 656 выходными токенами соответственно.
Сохранённые данные подтверждают усечение, а эффективный лимит на стороне
провайдера и роль строгой схемы остаются неизвестны. Повышать общий лимит
по этим данным оснований нет. Если понадобится диагностика, минимальное
изменение — добавить в benchmark параметр `--gigachat-max-tokens` с текущим
значением по умолчанию и сохранять фактическое значение и идентификатор запроса.
Сравнить один сбойный PDF и одну модель при 2500 и повышенном лимите в режиме
`schema`. При повторении сбоя проверить `prompt-json` с тем же лимитом
как отдельный эксперимент. Частичный JSON по-прежнему отклонять.

### План интеграции

Предварительный выбор для этого набора — Ultra для внешнего извлечения
и PyMuPDF Tables для локального режима. Один проход по восьми синтетическим
PDF оценивает пригодность для дальнейших испытаний. Медицинские документы
в этот прогон не входили.

1. Вынести из benchmark в модуль `documents` существующий HTTP-адаптер Ultra
   и Pydantic-схему без привязки к синтетическим PDF. Переиспользовать OAuth,
   загрузку, Structured Output, проверку `finish_reason`, учёт токенов и
   удаление в `finally`. Benchmark оставить клиентом этого же адаптера.
   PyMuPDF Tables запускать в существующем локальном subprocess.
2. Подключить внешний вызов как явную операцию в существующем Celery worker
   после проверки оригинала. Перед загрузкой проверять разрешение владельца
   на конкретный PDF, его версию и провайдера. Загрузка и обычный retry
   остаются локальными. Для включения доступа нужны адресный исходящий доступ
   к OAuth и API, проверка TLS, ключ только у worker и общий срок операции,
   оставляющий время на удаление до истечения аренды. В текущем Compose worker
   подключён к внутренним сетям. До разрешения на реальный пилот проверить
   условия обработки медицинских файлов для используемого аккаунта Ultra.
3. Сохранять исходный текст и локаторы вместе с текущей версией извлечения.
   Записи Ultra считать кандидатами до сверки со страницей, строкой и датой
   оригинала. Для скана требуется подтверждение по странице. Реконструкция
   модели не даёт координат. Для синтетического пилота достаточно результата
   в памяти. Постоянное хранение структурированного результата обсудить
   после пилота, если он нужен повторно для чата. Qdrant и LLM ответа
   в этой интеграции не участвуют.
4. До включения проверить синтетические регрессии для даты шапки, JSON `null`,
   сканов, прерывания и удаления файлов. При сбое сохранять доступность
   локального результата, а повторную отправку блокировать, пока не
   подтверждён статус предыдущего вложения. Использовать существующие
   worker и хранилища.

## Методы

- `pymupdf_text` вызывает действующий `extract_pdf()`, затем использует правила
  `table_measurements()` для допуска строк. Для scoring поля берутся из тех же
  ячеек плоского текста. В отчёте сохраняются текст, статус и локаторы.
- `pymupdf_tables` использует `find_tables(strategy="lines")` и встроенную
  стратегию `text` для страниц, где первый вызов не дал распознанных записей.
  Назначение колонок определяется существующим сопоставлением заголовков.
  Координаты строки возвращает PyMuPDF в пунктах PDF, отсчёт от верхнего левого
  угла. Оба локальных метода используют установленный PyMuPDF 1.26.6 без OCR.
- `gigachat` загружает один сгенерированный PDF на одну генерацию и проверяет
  ответ через Pydantic. Страница оценивается по эталону. Поле `quote` содержит
  реконструированную строку, координаты отсутствуют.

Оценки `strict_exact_match` и `normalized_exact_match` содержат Precision,
Recall, F1 и точность каждого из пяти полей записи.

- Strict сохраняет прежнее сравнение после NFC и свёртки пробелов. Регистр,
  десятичные разделители и символы тире различаются.
- Normalized дополнительно приводит к общему виду тире между границами
  диапазона, однозначные десятичные разделители, `µ` и `μ` в единицах и
  надстрочные показатели степени. Двусмысленные формы вроде `1,234` и
  `1.234` остаются разными. Знаки сравнения и отрицания, десятичные разряды,
  значения показателей степени и приставки единиц сохраняются. Исходные
  строки измерений в отчёте сохраняются.

Дубли считаются поштучно. Ошибка в поле полной записи даёт FP и FN.
`unmatched_measurements` показывает лишние записи без пары по названию,
включая дубли и реквизиты. При сопоставлении для отдельных полей учитываются
название, полные совпадения, дата и страница. В знаменатель входят поля
с непустым эталоном.

Страница, координаты и дословная цитата оцениваются отдельно. Координаты
засчитываются при верной странице и IoU строки ≥ 0,35. Для дословной цитаты
нужно точное вхождение строки в сохранённый текст указанной страницы с
соответствием эталонной записи. Строки из склеенных ячеек PyMuPDF и
ответа GigaChat учитываются как реконструкции. Ошибка запроса даёт
пустой результат для файла и отдельный код ошибки. Нулевой знаменатель
даёт `null`. Время GigaChat
включает OAuth при обновлении токена, загрузку, генерацию и удаление. Пропущенные
запросы не входят в latency. Токены берутся из `usage` и показывают только
значения, которые вернул API. Локальные PDF и отчёт хранятся в выбранном каталоге.

## Запуск из Git Bash

Нужен Python 3.12 с уже установленными зависимостями backend и dev для тестов.
В этом примере `python` указывает на нужное локальное окружение.

```bash
cd /c/workplace/Medical_AI_New/backend
python -m pytest -q tests/test_document_extraction_benchmark.py tests/test_gigachat_extraction.py
out_root="$(mktemp -d)"
python -m scripts.evaluate_document_extraction --output-dir "$out_root/local"
```

Ожидаются восемь PDF, `local/report.json` и два локальных метода в `summary`.
У `06-scan` оба метода должны вернуть пустой список, а у `08-no-measurements`
не должно быть ложных записей. Флаг `--fixture 01-grid` ограничивает все методы
одним эталонным файлом и подходит для пробного запроса. Для сравнения качества
используйте результаты на всех восьми файлах.

## Пересчёт сохранённого отчёта

Из того же каталога `backend` укажите старый отчёт и новый путь. Поддерживаются
форматы отчётов v1 и v2. Для этой команды достаточно самого JSON.

```bash
python -m scripts.evaluate_document_extraction \
  --rescore 'C:/path/to/report.json' \
  --report-output 'C:/path/to/report.rescored.json'
```

Команда пересчитывает оценки по сохранённым эталону и ответам, без генерации PDF,
сетевых вызовов и регистрации в MLflow. Она сохраняет SHA-256 исходного отчёта
в `rescored_from_sha256`, а также исходные значения, хеши корпуса и PDF,
задержку, токены и статус удаления. `--report-output` требует нового файла.
Корпус v1 в пересчитанном отчёте сохраняет свою версию и исходный дефект µ.
Чтобы проверить исправление шрифта, отдельно запустите локальное извлечение
`--fixture 02-borderless` на корпусе v2.

## Доступ к GigaChat Freemium

Откройте отдельный проект GigaChat API в личном кабинете. В настройках API
скопируйте **ключ авторизации** для OAuth. Сохраните его локально в
менеджере паролей. Для каждого запуска вводите ключ в Git Bash скрытым
вводом. Передаётся готовый ключ авторизации без префикса `Basic`.
OAuth scope для физлиц — `GIGACHAT_API_PERS`.
Если стандартному хранилищу не хватает нужных сертификатов, скачайте
официальные сертификаты и укажите путь к PEM bundle вне репозитория
через `GIGACHAT_CA_BUNDLE`. Сертификаты из PEM дополняют стандартное
хранилище Python. Проверка TLS и имени хоста обязательна.

[Начало работы с API](https://developers.sber.ru/docs/ru/gigachat/quickstart/ind-using-api) ·
[Авторизация REST](https://developers.sber.ru/docs/ru/gigachat/api/reference/rest/gigachat-api) ·
[Сертификаты](https://developers.sber.ru/docs/ru/gigachat/certificates)

| Аргумент | Модель | Что подтверждено документацией |
| --- | --- | --- |
| `lite` | `GigaChat-2` | Текстовый вход, обработка текстовых документов встроенной функцией. [Lite](https://developers.sber.ru/docs/ru/gigachat/models/gigachat-2-lite) |
| `pro` | `GigaChat-2-Pro` | Обработка документов встроенной функцией и отдельный анализ изображений. [Pro](https://developers.sber.ru/docs/ru/gigachat/models/gigachat-2-pro) |
| `max` | `GigaChat-2-Max` | Обработка документов и анализ изображений. В руководстве по Structured Output эта модель используется в примере без PDF. [Max](https://developers.sber.ru/docs/ru/gigachat/models/gigachat-2-max) · [Structured Output](https://developers.sber.ru/docs/ru/gigachat/guides/structured-output) |
| `ultra` | `GigaChat-3-Ultra` | Физлица в Freemium, адрес `api.giga.chat`, генерация через v1 или v2. Общая справка выделяет параллельные функции Ultra на v2. [Ultra](https://developers.sber.ru/docs/ru/gigachat/models/gigachat-3-ultra) · [REST v1](https://developers.sber.ru/docs/ru/gigachat/api/reference/rest/post-chat) |

Документация файлового API классифицирует PDF как текстовый документ. Анализ
изображений сам по себе не подтверждает OCR растровых страниц, переданных PDF.
Сочетание PDF, `function_call: "auto"` и строгого `response_format` нужно
проверить отдельным пробным запросом для каждой модели. Режим `schema` ставит
`response_format: json_schema`. Режим `prompt-json` задаёт ту же схему в
инструкции и валидирует ответ локально. Каждый режим запускается отдельно.
[Файловый API](https://developers.sber.ru/docs/ru/gigachat/guides/working-with-files)

```bash
# Выполнить в том же Git Bash после локальной проверки.
read -rsp 'Ключ авторизации GigaChat: ' GIGACHAT_CREDENTIALS
printf '\n'
export GIGACHAT_CREDENTIALS
# При необходимости укажите путь в формате, понятном Windows Python.
# export GIGACHAT_CA_BUNDLE='C:/path/outside/repo/gigachat-ca.pem'

python -m scripts.evaluate_document_extraction \
  --fixture 01-grid --gigachat-model max --gigachat-mode schema \
  --allow-synthetic-upload --output-dir "$out_root/max-smoke"

python -m scripts.evaluate_document_extraction \
  --gigachat-model max --gigachat-mode schema \
  --allow-synthetic-upload --output-dir "$out_root/max-full"

unset GIGACHAT_CREDENTIALS GIGACHAT_CA_BUNDLE
```

Выполняйте полный запуск после проверки пробного отчёта. Для других моделей
меняйте `--gigachat-model` и каталог. При несовместимости режима `schema`
можно повторить пробный запуск с `--gigachat-mode prompt-json` в новом каталоге.
Успешный запрос сообщает `deletion: "deleted"` после HTTP 200 от метода
удаления. Это удаление из доступных вложений по контракту API. При `unknown`
или `failed` скрипт прекращает следующие загрузки, сохраняет имя отправленного
файла и ID, если тот известен, и возвращает ненулевой код. В этом случае
проверьте список файлов выделенного проекта и подтвердите удаление по имени
или ID через файловый API. Ошибки генерации и очистки видны отдельно.
[Удаление файла](https://developers.sber.ru/docs/ru/gigachat/api/reference/rest/file-delete)

## Необязательный MLflow

При уже работающем локальном MLflow добавьте к любой команде
`--mlflow-uri http://127.0.0.1:5000`. Скрипт пишет числовые агрегаты в
эксперимент `medical-ai-synthetic-document-extraction` через Tracking REST
API. В MLflow передаются агрегированные числа и параметры воспроизводимости,
включая выбранную модель и режим. Отчёт сохраняется
локально даже при сбое регистрации. В базовом запуске MLflow не используется.
[MLflow Tracking REST API](https://mlflow.org/docs/latest/api_reference/rest-api.html)
