# **Техническое задание**

## **Medical AI — интеллектуальная платформа анализа медицинских документов**

Версия 1.0 · 13 ноября 2026 года · Новая разработка

Мы создаём **полноценный программный продукт Medical AI** с новой кодовой базой, собственной инфраструктурой, гибридным подключением LLM, системой RAG и возможностью дальнейшего промышленного масштабирования.

Основной принцип архитектуры: **готовая LLM выполняет интеллектуальный анализ, а наше приложение управляет документами, данными, источниками знаний, инструментами, безопасностью и достоверностью результатов.**

Проект не зависит от прежнего репозитория. Все компоненты создаются заново.

## **1. Назначение и функциональность**

Medical AI — веб-платформа, в которой зарегистрированный пользователь может загружать медицинские документы и общаться с AI-ассистентом в формате привычного LLM-чата.

Система должна обеспечивать:

1. Регистрацию, авторизацию и личный кабинет.
2. Загрузку PDF, DOCX, TXT, JPG и PNG.
3. Извлечение текста из документов, включая OCR.
4. Хранение оригиналов документов и истории обработки.
5. Диалог с LLM с сохранением контекста и истории переписки.
6. Поиск по личным документам через RAG.
7. Использование отдельной базы проверенных медицинских знаний.
8. Контролируемый поиск актуальных клинических рекомендаций в интернете.
9. Извлечение лабораторных показателей с помощью LLM.
10. Сравнение результатов исследований по датам, построение графиков и объяснение изменений.
11. Выбор локальной или облачной LLM.
12. Формирование отчётов с указанием источников.
13. Администрирование моделей, медицинской базы знаний и системных параметров.

Система предназначена для информационной поддержки и анализа медицинских данных, но не должна самостоятельно устанавливать окончательные диагнозы, назначать или изменять лечение.

## **4. Гибридный LLM Gateway**

Это центральный интеллектуальный компонент платформы.

### **4.1. Поддерживаемые провайдеры**

| Провайдер         | Способ подключения                 |
| ----------------- | ---------------------------------- |
| Ollama / Qwen     | Локальный HTTP API                 |
| OpenAI GPT        | Официальный API                    |
| DeepSeek          | Официальный API                    |
| YandexGPT         | Yandex Cloud API                   |
| GigaChat          | API с соответствующей авторизацией |
| Другие провайдеры | Через новые адаптеры               |

Для каждого провайдера предусматриваются настройки модели, лимитов токенов, тайм-аутов, параметров генерации, стоимости и доступных возможностей.

### **4.2. Требования к Gateway**

- Единый внутренний интерфейс вызова моделей.
- Поддержка потоковой генерации (streaming).
- Структурированный JSON-вывод с проверкой Pydantic.
- Обработка ошибок, rate limits и недоступности провайдера.
- Учёт потребления токенов и стоимости.
- Раздельная конфигурация генеративных и embedding-моделей.
- Возможность подключения нового провайдера без изменения логики чата.
- Запрет автоматической передачи медицинских данных во внешние API без явного согласия пользователя.
- Отсутствие скрытого переключения с локальной модели на облачную.

Различия API, авторизации и функциональности провайдеров должны обрабатываться адаптерами. Нельзя предполагать, что все модели поддерживают одинаковые режимы JSON, streaming и tool calling.

## **5. Работа с документами**

### **5.1. Загрузка**

Поддерживаемые форматы: PDF, DOCX, TXT, JPG, PNG.

Для файлов устанавливаются настраиваемые ограничения размера, количества страниц и времени обработки. Проверяется фактический формат, а не только расширение.

### **5.2. Техническая обработка**

Последовательность:

`Upload → MinIO → Extract/OCR → Normalized Text → Chunking → Embeddings → Qdrant`

Для каждого фрагмента сохраняются `document_id`, `user_id`, версия документа, номер страницы или иной локатор, текст и сведения о способе извлечения.

Текст должен сохраняться независимо от того, удалось ли LLM извлечь лабораторные показатели.

### **5.3. Анализ LLM**

LLM должна уметь извлекать из документа:

- название показателя;
- измеренное значение;
- единицу измерения;
- референсный интервал, если указан;
- дату исследования;
- название лаборатории, если указано;
- ссылку на исходный фрагмент.

Для полного извлечения результатов нельзя ограничиваться только `top-k` фрагментами RAG: весь релевантный текст документа должен быть обработан с учётом контекстного окна модели.

LLM возвращает структурированный результат. Backend проверяет формат, числовые значения, происхождение и согласованность с исходным текстом. Сомнительные значения отправляются на подтверждение пользователю.

**Собственный универсальный медицинский парсер не разрабатывается.** Допускаются технические преобразования чисел, дат, единиц измерения и проверки корректности.

## **6. RAG и медицинская база знаний**

Предусмотреть два логически независимых корпуса.

**Персональный RAG:** документы пользователя. Поиск строго ограничен его правами доступа.

**Медицинский RAG:** проверенные клинические рекомендации, медицинские справочники, нормативные документы и научные материалы.

Медицинские источники должны иметь метаданные: издатель, ссылка, версия, дата публикации, дата проверки, юрисдикция, область применения и статус актуальности.

Поисковый механизм должен поддерживать семантический поиск, метаданные, фильтрацию и при необходимости гибридный retrieval с reranking.

Для каждого ответа с опорой на документы должны предоставляться проверяемые ссылки на источники. Если надёжный источник не найден, система должна явно сообщить об этом.

### **6.1. Интернет-поиск**

Отдельный Backend-инструмент выполняет поиск по разрешённым медицинским источникам. Система должна учитывать дату публикации, достоверность и применимость рекомендаций.

Внешний веб-поиск не должен автоматически превращать найденные страницы в проверенную медицинскую базу знаний.

### **6.2. Гибридный поиск по личным документам**

После этапа 5 персональный RAG поддерживает серверные режимы `dense` и
`hybrid`. По умолчанию используется `dense`. В гибридном режиме BGE-M3 и
BM25 дают кандидатов для нативного RRF в Query API Qdrant 1.15.5. Обе ветки
фильтруются по владельцу и поколению, а выдача повторно проверяется по PostgreSQL.
Backfill переносит существующие dense-векторы в версионированную коллекцию и
строит BM25 на локальном сервере Qdrant. Приёмка включает сравнение качества
и задержки с прежним Hybrid RAG и dense, включая точность дат и значений.
Подробности и отдельный анализ релевантности источников чата описаны
в [HYBRID_RAG.md](HYBRID_RAG.md).

## **7. Чат, аналитика и отчёты**

Чат поддерживает историю диалогов, выбор модели, прикрепление документов, потоковые ответы, ссылки на источники и обработку ошибок.

Аналитика должна включать сравнение лабораторных показателей по датам, выявление изменений, построение временных рядов и экспорт результатов.

**Точные вычисления выполняются через Python/SQL**, а не свободной генерацией LLM. Модель интерпретирует результаты расчётов, но не является единственным источником числовой истины.

Медицинские рекомендации формируются с учётом имеющегося контекста и клинических источников, с указанием ограничений. Система не должна выдавать персонализированные назначения лекарств как окончательные медицинские решения.

## **8. Безопасность и защита медицинских данных**

Поскольку приложение работает с чувствительной медицинской информацией, безопасность закладывается в архитектуру с самого начала.

Обязательные требования:

- Авторизация, безопасные cookie-сессии, защита CSRF и разграничение доступа.
- Изоляция данных пользователей в PostgreSQL, MinIO и Qdrant.
- Проверка принадлежности документа при каждом обращении к API и RAG.
- Шифрование соединений при внешнем доступе, защищённое хранение секретов.
- Согласие на передачу данных внешним LLM-провайдерам, возможность его отзыва.
- Отсутствие медицинских данных, паролей и API-ключей в логах.
- Защита от prompt injection в загруженных документах и веб-страницах.
- Проверка файлов, ограничение ресурсов и защита от злоупотребления API.
- Удаление документов из MinIO, PostgreSQL и Qdrant, включая отложенные задания.
- Резервное копирование и восстановление данных.
- Аудит административных действий и обращений к внешним моделям.

Юридические требования к обработке медицинских данных должны быть определены отдельно для юрисдикций, в которых будет работать продукт, до допуска реальных пользователей.

## **9. Инженерная инфраструктура**

### **9.1. Docker**

Все основные компоненты запускаются через Docker Compose.

Необходимы отдельные конфигурации для локальной разработки и production-развёртывания, persistent volumes, healthchecks, переменные окружения и изолированные сети.

Данные должны сохраняться после пересоздания контейнеров. Удаление томов не должно входить в стандартные процедуры обновления.

### **9.2. GitHub и CI/CD**

С первого этапа создать Git-репозиторий и конфигурацию GitHub Actions.

CI должен включать:

- Ruff и проверку типов Python.
- ESLint и проверку TypeScript.
- Pytest для Backend.
- Тесты Frontend.
- Проверку миграций.
- Интеграционные тесты с тестовыми PostgreSQL, MinIO, Redis и Qdrant.
- Проверку зависимостей и секретов.
- Сборку Docker-образов.
- Публикацию версионированных образов в GitHub Container Registry.

CD должен предусматривать раздельные окружения staging и production, защищённые секреты, ручное подтверждение production-развёртывания, миграции с проверкой совместимости, smoke-тесты и rollback приложения.

Нельзя считать rollback Docker-образа автоматическим откатом схемы PostgreSQL. Миграции должны проектироваться с учётом обратной совместимости.

### **9.3. Тестирование**

| Уровень        | Что проверяем                                 |
| -------------- | --------------------------------------------- |
| Unit           | Сервисы, валидаторы, адаптеры                 |
| Integration    | API, БД, хранилища, очереди                   |
| E2E            | Регистрация, загрузка, чат, анализ            |
| RAG evaluation | Recall\@k, MRR, качество источников           |
| LLM evaluation | Корректность извлечения, groundedness, отказы |
| Security       | ACL, инъекции, утечки, доступ к чужим данным  |
| Performance    | Время ответа, нагрузка, очереди, память       |

Для извлечения показателей предусмотреть размеченный тестовый набор и метрики точности по названиям, значениям, единицам и датам.

Результаты тестирования сохраняются в CI. При этом локальный запуск тестов выполняет пользователь.

### **9.4. Мониторинг**

Предусмотреть структурированные логи, метрики, трассировку запросов и фоновых задач.

Отслеживать задержку LLM, стоимость API, количество ошибок, длительность индексации, размер очередей, состояние баз данных и доступность сервисов.

Prometheus, Grafana и OpenTelemetry вводятся поэтапно, но точки инструментирования закладываются при разработке сервисов.

### **9.5. MLflow Tracking и Model Registry — дополнение к ТЗ**

Дополнение включено по прямому требованию пользователя к этапу 1.

- Отдельный сервис `mlflow` с MLflow Tracking UI, локально доступным на localhost.
- PostgreSQL — backend store экспериментов, запусков, параметров, метрик,
  метаданных и версий Model Registry. Используется отдельный экземпляр `mlflow-db`
  с отдельными учётными данными и persistent volume, независимо от основной БД.
- MinIO — S3-compatible artifact store для отчётов, графиков, результатов
  экспериментов и артефактов моделей. Отдельный закрытый bucket и пользователь
  с ограниченными этим bucket правами; клиенты используют MLflow artifact proxy.
- Все подключения и секреты настраиваются через переменные окружения.
  Секреты не хранятся в коде, образах, Git и CI-логах.
- Обязательны healthcheck, зависимости запуска, постоянное хранение и изоляция сетей.
- Подготовлены URI Tracking/Registry и имя эксперимента для будущих экспериментов
  с LLM, embedding-моделями, RAG, версиями промптов и evaluation.
- Model Registry должен поддерживать последующее версионирование моделей,
  метаданные происхождения, версии артефактов и сопоставление с run ID.
- Архитектура сохраняет возможность MLflow Tracing для LLM-вызовов.
  На этапе 1 autologging, tracing и бизнес-интеграция не включаются.
- До включения логирования/трассировки необходимо определить очистку медицинских
  данных, согласия, доступ, retention и удаление данных из всех хранилищ.
- Внешний доступ к UI допустим только после настройки аутентификации и TLS.
  Локальный Compose не является готовым production-развёртыванием.

Критерии приёмки этапа 1: пользователь проверяет доступность Tracking UI,
healthchecks, создание синтетического run, загрузку/скачивание артефакта через
proxy, API Model Registry и сохранение данных после пересоздания контейнеров.
Проверки и запуск выполняет пользователь согласно разделу 13.

## **10. Расширяемость: LangGraph и Apache Airflow**

Архитектура должна позволять дальнейшее подключение этих технологий без масштабного переписывания Backend.

**LangGraph** будет использоваться для сложных AI-workflows: планирования действий, последовательного вызова RAG, SQL/Python и веб-поиска, проверки результатов, управления состоянием и согласования чувствительных операций.

**Apache Airflow** будет использоваться для периодических ETL/ELT-процессов: обновления медицинской базы знаний, массовой переиндексации, проверки актуальности источников, регулярных аналитических и служебных задач.

LangGraph и Airflow имеют разные роли и не должны дублировать друг друга или заменять Celery без необходимости.

На первоначальных этапах их не устанавливаем. Для дальнейшей интеграции предусматриваем независимые интерфейсы инструментов, идемпотентные задания и версионирование результатов.


Структура логическая, а не требование создавать пустые каталоги заранее. Новые модули добавляются при реализации соответствующих функций.

## **12. Критерии готовности продукта**

Продукт считается готовым к промышленному использованию после выполнения и проверки следующих условий:

1. Пользователи могут безопасно регистрироваться и работать со своими данными.
2. Поддерживается загрузка всех заявленных форматов документов.
3. Документы корректно обрабатываются, индексируются и удаляются.
4. Чат работает с локальной LLM и подключаемыми облачными провайдерами.
5. Ответы по документам сопровождаются проверяемыми источниками.
6. Медицинские рекомендации опираются на управляемую базу знаний или проверенные внешние источники.
7. Лабораторные показатели извлекаются с измеренным качеством и возможностью подтверждения.
8. Числовая аналитика воспроизводима и не зависит от случайности генерации LLM.
9. Пользователь не может получить доступ к чужим документам, векторам и чатам.
10. Работают автоматические проверки, CI/CD, мониторинг, резервное копирование и восстановление.
11. Система проходит согласованные нагрузочные и security-тесты.
12. Документированы процедуры развёртывания, эксплуатации, обновления и восстановления.

Целевые показатели производительности, точности извлечения, доступности и допустимой стоимости LLM должны быть установлены на основе измерений, а не придуманных значений.

# **13. Правила работы Codex**

Это обязательная часть ТЗ, которая должна быть записана в `AGENTS.md` нового проекта.

**Codex пишет и изменяет код. Пользователь выполняет команды.**

Codex разрешено читать исходники, искать зависимости, создавать и изменять файлы проекта, писать тесты, миграции, Docker-конфигурации и GitHub Actions.

Codex запрещено самостоятельно запускать:

- Docker, Docker Compose и сборку образов.
- Pytest, линтеры, typecheck и E2E-тесты.
- Приложения, миграции и серверы.
- Установку зависимостей.
- Git commit, push, reset и операции с удалённым репозиторием.
- Команды удаления данных и Docker volumes.

Для чтения и статического анализа разрешены безопасные shell-команды, не изменяющие файлы.

**Все команды запуска предоставляются пользователю в формате Git Bash для Windows.**

После каждого задания Codex обязан сообщать, какие файлы изменены, что реализовано, какие проверки пользователь должен выполнить, какие результаты ожидаются и какие ограничения остались.

Запрещено утверждать, что тесты пройдены, если пользователь их не запускал.

Переход к следующему этапу допускается только после проверки результатов пользователем.
