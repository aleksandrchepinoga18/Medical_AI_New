Документ фиксирует результаты локальной проверки и порядок действий для владельца репозитория. Команды предназначены для Git Bash в Windows. Локальный репозиторий уже существует. На момент проверки `main` указывает на `6a1953f`, рабочая ветка `feature/stage6-6-evaluation` — на `482103d`. У `main` есть исторический GitHub Actions workflow, поэтому начальная публикация и запуск обновлённого CI описаны отдельно.

## Что проверено локально

Проверены состав индекса, отслеживаемое рабочее дерево и 23 достижимых коммита из локальных ссылок, включая резервные ветки. Сканер прочитал 464 уникальных blob и проверил пути и сообщения коммитов. По настроенным правилам после сверки тестовых фикстур совпадений с рабочими ключами, токенами, паролями, закрытыми ключами или идентификаторами пациентов не обнаружено. Совпавшие ранее литералы оказались шаблонными значениями и синтетическими отрицательными тестами. Полная проверка отсутствия чувствительных данных требует просмотра подготовленного diff и сведений о происхождении файлов. Сканер не просматривает локальные игнорируемые файлы, потерянные объекты Git, внешние хранилища или содержимое изображений и архивов.

В Git остаются исходники, конфигурации с шаблонными значениями, `AGENTS.md`, руководство Codex, ТЗ, архитектура, записанные решения, инструкции приёмки, синтетические фикстуры и обезличенные агрегаты. Локальные заметки и отладочные артефакты размещайте в `scratch/`, `evaluation-reports/` или вне проекта. Хранение рабочих ключей, резервных копий, медицинских файлов, диагностических экспортов и пользовательских данных в приватном GitHub тоже исключается.

## 1. Проверить и зафиксировать только подготовленные изменения

```bash
git --no-optional-locks status --short --branch
git ls-files -ci --exclude-standard
python -B .github/scripts/audit_git.py --history --worktree
```

Ожидается пустой вывод `git ls-files -ci --exclude-standard` и `Findings: 0` у сканера. Если есть находка, остановите публикацию. Для случайно добавленного рабочего файла проверьте индекс и снимите с будущего коммита только этот путь, сохранив локальный экземпляр. Для рабочего секрета из любого публикуемого коммита сначала отзовите или замените секрет, затем согласуйте очистку истории либо подготовку чистой стартовой истории и повторите аудит. Простое добавление пути в `.gitignore` не удаляет прежние коммиты. Рабочие значения не переносите в issues, PR и чаты.

На ветке `feature/stage6-6-evaluation` добавьте только согласованные пути.

```bash
git add -- README.md AGENTS.md .gitignore .dockerignore \
  .github/workflows/ci.yml .github/scripts/audit_git.py \
  docs/TZ.md docs/CODEX_TASKS.md docs/OPERATIONS.md docs/PROJECT_AUDIT.md docs/GITHUB_SETUP.md
git diff --cached --name-status
git diff --cached --check
git commit -m "Prepare private GitHub repository and baseline CI"
python -B .github/scripts/audit_git.py --history --worktree
```

Перед commit просмотрите staged diff локально. Повторный скан после commit проверяет именно сохранённые Git-объекты. Отклонение от ожидаемого набора файлов требует проверки перед push.

## 2. Создать приватный репозиторий и отправить две ветки

1. Создайте пустой **Private** репозиторий в GitHub без инициализации README, лицензией и `.gitignore`. Проверьте владельца и видимость.
2. Временно отключите Actions в настройках репозитория. Это предотвращает запуск исторического workflow при первой отправке `main`.
3. Добавьте `origin` с SSH-адресом или чистым HTTPS-адресом. Для HTTPS используйте менеджер учётных данных. URL с PAT или паролем оставляет секрет в локальной конфигурации Git.

```bash
git remote add origin git@github.com:OWNER/REPOSITORY.git
git push --no-follow-tags -u origin main
git push --no-follow-tags -u origin feature/stage6-6-evaluation
```

Если `origin` уже существует, сначала локально сверяйте его с подготовленным адресом и владельцем. Проверьте на GitHub, что ветка по умолчанию — `main`. Включите Actions до создания PR. Разрешите только нужные закреплённые Actions. В настройках workflow permissions оставьте токен read-only и отключите право Actions создавать и одобрять PR. Секреты GitHub для этой конфигурации не нужны.

## 3. Pull Request и контроль результатов

Создайте Pull Request с базовой веткой `main` и compare-веткой `feature/stage6-6-evaluation`. Проверьте вкладку **Files changed**, историю и видимость. После первого запуска найдите результаты в **Checks** и **Actions**. В правилах защиты `main` включите merge через PR и обязательные проверки по фактическим именам job, если настройки приватного репозитория это поддерживают. Проверьте ограничения организации, если PR не стартует или GitHub не находит Action по SHA.

| Job | Что должно выполниться |
|---|---|
| `repository-audit` | Сканер проверяет Git-деревья и историю, доступные в checkout. Совпадение завершает проверку ненулевым кодом. |
| `backend` | `pip check`, `pip-audit` по установленным зависимостям, Ruff, mypy и Pytest unit с JUnit. |
| `frontend` | Установка зависимостей через `npm ci` по `frontend/package-lock.json`, `npm audit` с порогом high/critical, ESLint, TypeScript и Vitest с JUnit. |
| `migrations-auth` | Alembic генерирует SQL offline. Существующие тесты затем выполняют upgrade, повторный upgrade, schema drift и auth на временной PostgreSQL сервиса runner. |
| `document-integration` | Отдельный синтетический Compose проверяет загрузку, обработку, outbox и worker через временные PostgreSQL, Redis и MinIO. |
| `docker-build (backend)`, `docker-build (frontend)` | Docker собирает runtime-образы. Цель frontend выполняет реальный `next build` и проверяет standalone-артефакт. Публикации образов нет. |
| `compose-config` | Топологии dev и production валидируются с шаблонной конфигурацией. |

Проверяйте наличие выполненных тестов и причины пропусков, а не только цвет job. Ошибку установки, недоступность advisory-сервиса или найденную уязвимость устраняйте как отдельную задачу. `pip-audit` и `npm audit` обращаются к источникам advisories на GitHub-hosted runner. Проверка не охватывает CVE всех системных пакетов образов или отдельного окружения MLflow. После принятия PR проверьте повторный CI на `main`.

Базовый CI использует GitHub-hosted Linux, пустые синтетические хранилища и моки внешних операций в тестах. Отдельный job для Chat/Knowledge/RAG можно добавить после проверки существующих `compose.chat-test.yaml`, `compose.rag-test.yaml` и флагов `RUN_CHAT_INTEGRATION`/ `RUN_RAG_INTEGRATION` на runner. Для проверки реальных эмбеддингов зафиксируйте модель и оцените время загрузки, память и кэш на синтетической среде. Cloud evaluation с ключом и MLflow import остаются ручной процедурой из изолированного стенда. Автоматический деплой, GHCR и доступ к production или медицинским данным не входят в этот CI.
