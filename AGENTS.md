# Правила работы Codex

Источник требований: [docs/TZ.md](docs/TZ.md), раздел 13.

**Codex пишет и изменяет код. Пользователь выполняет команды.**

Codex разрешено читать исходники, искать зависимости, создавать и изменять файлы
проекта, писать тесты, миграции, Docker-конфигурации и GitHub Actions.

Codex запрещено самостоятельно запускать:

- Docker, Docker Compose и сборку образов.
- npm, npx и другие команды исполнения, кроме безопасного чтения и статического анализа.
- Pytest, линтеры, typecheck и E2E-тесты.
- Приложения, миграции и серверы.
- Установку зависимостей.
- Git-команды, меняющие индекс, рабочее дерево, ссылки или историю, и операции с удалённым репозиторием.
- Команды удаления Docker volumes, баз данных и пользовательских файлов.

Для чтения и статического анализа разрешены безопасные shell-команды,
не изменяющие файлы. Файлы изменяются средствами редактирования.
При аудите Git разрешено читать локальные метаданные и объекты. Для находок
сообщать только тип, путь и ревизию. Значения секретов и медицинские данные
не включать в вывод команд, логи, комментарии и отчёты.

**Все команды запуска предоставляются пользователю в формате Git Bash для Windows.**

После каждого задания Codex обязан сообщать, какие файлы изменены, что реализовано,
какие проверки пользователь должен выполнить, какие результаты ожидаются
и какие ограничения остались. Запрещено утверждать, что тесты пройдены,
если пользователь их не запускал. Переход к следующему этапу допускается
только после проверки результатов пользователем и его явного подтверждения.

## Проектные ограничения

- Не менять `.env` и секреты без согласования с пользователем.
- Не устанавливать дополнительные сервисы без обоснованной необходимости;
  команды установки и запуска выполняет только пользователь.
- Модульный монолит; новые бизнес-модули создавать только при реализации функций.
- Никаких реальных медицинских данных, секретов и ключей в репозитории и логах.
- Никаких внешних LLM-вызовов или скрытого переключения провайдеров без согласия.
- MLflow autologging и tracing не включать без отдельного согласования и правил
  очистки данных, доступа и хранения.
- Не удалять persistent volumes и не выполнять миграции автоматически агентом.
- Не подменять проверки фиктивными тестами или заявлениями о совместимости.

## Документация и CI

- Хранить в Git ТЗ, архитектуру, инструкции, принятые решения, проверенные
  синтетические фикстуры и обезличенные итоговые метрики. Локальные заметки,
  снимки экрана, сырые отчёты, выгрузки конфигураций и резервные копии
  хранить вне Git. [Порядок подготовки репозитория](docs/GITHUB_SETUP.md)
- Для CI использовать изолированные синтетические окружения, минимальные
  права токена и внешние GitHub Actions, закреплённые полным SHA. Подключение
  к production или передача рабочих ключей требуют отдельного согласования.
